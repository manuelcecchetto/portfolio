10 月 2 日，我为 [pi](https://pi.dev) 做了一个桌面应用的第一次提交。pi 是我每天都在用的编程代理。九天过去了，现在有 528 次提交、44 个版本，大约 88,000 行 TypeScript、Swift 和 CSS 代码。应用叫 [pi-gna](https://pi-gna.com)，从第二天开始，它的大部分代码就是应用内的代理写的。

这是这九天的记录。

## 为什么开始做

两件事同时让我不爽。

第一件是 pi 1.0。我很喜欢 pi，它小巧、稳定，我还为它写了不少扩展，从[上下文垃圾回收](/zh/blog/let-the-agent-decide-when-to-forget)到 ATP 编排器，再到终端里的 7TV 表情。但 1.0 版本在终端里感觉很慢，而我一天大部分时间都盯着终端。我很讨厌这一点。

第二件是我在网上看到的内容。有人会写："我真的很想试试 Opus，但 Codex 的 Computer Use 太好用了，我离不开它。" 大家选择代理框架是看 UI 功能，模型反而排在后面。与此同时，显而易见的另一个选择 Claude Code，要让我用它得先把我杀了。

pi 已经有我在乎的东西：可靠、没有臃肿、还有我自己写的扩展。它只是缺一个窗口。于是我在终端里打开 pi，让它给我做一个。

第一次提交的名字叫 "pi studio"。10 月 3 日 00:18，它改名为 pi-gna，取自意大利语的 *mano a pigna*，也就是 🤌 这个手势。吉祥物 Pigna 就是这只手，被画进了莫奈、梵高和葛饰北斋的画里。

## 工作原理

pi-gna 里的每个聊天都是一个 `pi --mode rpc` 进程，运行的就是你本机已经装好的 pi。应用通过 stdin 和 stdout 跟它通信，把返回的内容画出来：消息、工具调用、diff、思考过程、上下文用量表。会话用的是 pi 自己的会话文件，所以我可以在终端里开个东西，在应用里接着聊，然后再回到终端。我的模型、登录信息、skills、扩展和 MCP 服务器，都是我在 pi 里已经配好的那些。

这个决定让项目保持可控。pi-gna 不需要自己的代理循环、自己的插件系统或自己的配置。扩展向 pi 请求确认或输入时，pi-gna 会在输入框上方画一张卡片，而不是弹出终端提示。应用给代理新增的东西，比如浏览器、Computer Use 或 Kanban 看板，都是以 pi 扩展提供的工具形式交给 pi 的，和其他扩展没有区别。

## 从 pi 到在 pi-gna 里开发 pi-gna

第一天都在终端里做：RPC 桥接、对话记录、输入框、会话列表，然后是一个 pi 能操作的浏览器面板。应用能用了，我就搬了进去，从那以后，pi-gna 就是在 pi-gna 里开发的。

提交记录能看出这个转变。第一天和第二天分别有 22 和 15 次提交，这是你自己敲代码、自己读每一行时的节奏。第三天是 94 次，第四天是 102 次。

变的是我分派工作的方式。根据想法的大小，我用两种工具。

### 小想法用 Kanban

pi-gna 的每个项目都有一个 Kanban 看板。我用自己的话描述一个任务，一个便宜的模型会在后台给它起标题、打标签。在卡片菜单里，我可以让一个新聊天去解决它。这个聊天会拿到自己的 git worktree 和独立分支，所以我的工作目录不会被动到。完成之后，卡片会移到 In review，我再去看。

我就是这么用的：想到一个功能，写一张卡片，推出去。然后再来一张。应用里一共合并了 89 次，很多来自 `pigna/...` 分支，都是卡片聊天开出来、做完再交回来的。你在 pi-gna 里看到的很多小东西，比如右键菜单、长聊天旁边的导轨、悬停时显示的 tok/s 图表，最初都只是卡片上的一句话。

### 大想法用 ATP

遇到大的东西，我用 ATP，也就是 [Agent Task Protocol（代理任务协议）](/zh/blog/how-atp-works)。这个东西是我大约一年前想出来的：一个计划就是一张图，每个节点有指令、依赖关系、生命周期状态和完成报告，代理认领节点后并行执行。在这个领域，一年已经很久了，我还是没找到更好的方式把大块工作交给代理。这是这个项目里我唯一会一直坚持的东西。

pi-gna 有一个 ATP 页面，展示计划的图，还有一个架构师聊天，可以和你一起起草计划。应用里最大的几个功能都是这样做出来的。Computer Use 的计划有 18 个节点，从设计验证到 Swift 辅助程序、权限策略存储、设置页面、对话渲染、CI 打包，再到在我真实的桌面上做两轮实机验证。iPhone 远程访问是另一个计划，大部分是在 10 月 4 号到 5 号之间的一个通宵跑完的。

## Computer Use

Computer Use 让这个应用在我看来像是做完了。开启之后，pi 可以在原生 Mac 应用里干活，同时你照常用电脑。它读取应用的无障碍树和窗口截图，然后用它自己的光标点击和输入。它不会移动你的鼠标，也不会抢你的键盘焦点。每个应用你可以选择允许一次或始终允许，按 Esc 就能停止。

第一版不是这样工作的。设计验证时发现，向后台应用发送事件最直接的办法，也就是直接投递到它的进程，会被 TextEdit 忽略。于是计划退而求其次：把应用切到前台，移动真正的光标。这就等于接管了我的桌面，而这正是我最不想要的。

我相信，软件一旦发布，实际上就是免费的。任何人都可以看它的行为、从中学习，然后做出更好的东西。Codex 的 Computer Use 已经做到了我想要的效果，所以我在计划里加了一个节点：弄清楚 Codex 是怎么在不抢焦点的情况下驱动后台应用的，并用 Swift 证明同样的做法可行。编排器用 `nm` 和 `strings` 看了 Codex 辅助程序二进制文件里的符号名。`SystemFocusStealPreventer`、`SyntheticAppFocusEnforcer`、`VirtualCursor` 这些名字足以形成假设。一个 worker 做了个验证原型证明了它，然后在输入节点开始之前，设计文档被修改了。

从设计验证到端到端实机检查，整个 Computer Use 计划大约花了一个上午。然后是那些比功能本身花更长时间的细节：用稳定证书给辅助程序签名，这样 macOS 的权限在更新后不会丢；还有当 macOS 拒绝弹出自己的提示时，用来处理屏幕录制权限的流程。

## Lamenting：没成功的功能

不是所有东西都成功了。我纸面上最喜欢的想法是 laments（吐槽）。当 pi 需要的工具缺失、不可用或者失败时，它会在项目的 Lamenting 看板上提交一条吐槽，评级为 😒 烦人、😠 费钱或 🤬 阻塞，然后继续用变通方案干活。我本来想象自己每天早上读这些吐槽，一条一条地修我的配置。

实际上效果很一般。它从来没有变成我设想中的反馈循环。这九天里最清楚的教训是：现在做东西的成本已经低到可以在没人验证它值不值得做之前就把它做出来。

## 九天发布 44 次

发布只需要一条命令。`pnpm release` 会把 changelog 里 Unreleased 下的内容移到新版本下面，打上标签，然后 CI 为 Apple silicon 和 Intel 构建 DMG。应用会检查 GitHub 上的更新，你退出时自动安装。在这九天的最后一天，我发布了 v0.12 到 v0.15.1：可以导入 Codex 和 Claude Code 的聊天、一个用量面板、GPT 模型的 Fast 模式，还有一个实验性的功能，让聊天能在应用重启后保留下来。

现在 pi-gna 还有一个你可以和 pi 共享的浏览器面板、文件预览、每个项目的 GitHub issue 和 PR、聊天导入、插件，以及通过 Tailscale 从我的 iPhone 远程访问。手机端是由 Mac 提供服务的一个 Web 应用。pi、代码仓库和 Computer Use 都留在 Mac 上。

## 实际上是怎么过来的

我有很严重的 ADHD，而这个项目和我的正式工作是同时进行的。在 [Casus](https://getcasus.com)，那一周我大约做了 300 次提交。pi-gna 的提交时间覆盖了每一个小时，除了凌晨 3 点到 5 点左右，最忙的时段是午夜。

听起来很累，但实际感觉并不累。这种工作方式很适合我的脑子。一个想法冒出来，我写一张卡片，代理就开始做，而我还在想下一个。一个大想法变成计划，计划在我做别的事情的时候跑。我的工作是决定什么应该存在，检查回来的成果，并让整体保持连贯。我读 diff，我打开应用，错了就把工作退回去。

pi-gna 主要是为我自己做的。它把我工作方式的所有东西都串在了一起：以 pi 为骨干，大计划用 ATP，小任务用看板，浏览器和 Computer Use 当手脚，离开书桌时用手机。已经有几个朋友开始用了。

要说这九天最接近的描述，就是我一直感觉自己很有力量，也一直掌控着局面。我的工具第一次按照我的方式工作了。
